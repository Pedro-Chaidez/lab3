1. Program understanding

Describe the input format and the main branches in the parser.

The parser (`parse_image_message` in `image.c`) accepts byte sequences starting
with the 5-byte header `IMG2;` followed by semicolon-terminated `KEY=VALUE;`
fields (`FMT`, `OP`, `AUTH`, `W`, `H`, and `DATA`) in any order.
- Format validation (`format_channels`): Requires `FMT` to be `GRAY` (1 channel),
  `RGB` (3 channels), or `META` (1 channel).
- Dimension validation (`parse_dimension` & `multiply_size`): Requires `W` and
  `H` to be non-empty decimal strings representing integers from 1 through 64,
  and computes `pixel_count = width * height` and
  `bytes_needed = pixel_count * channels`.
- Operation branches:
  1. `OP=INFO`: Succeeds immediately (`return 1`) once format and dimensions
     are valid.
  2. `OP=CHECK`: If `FMT=META`, requires `DATA` to start with the prefix
     `CS165:`. Otherwise (`GRAY` or `RGB`), requires `DATA` to be present with
     exact length `payload.len == bytes_needed`.
  3. `OP=THUMB`: Requires `AUTH=YES` and `FMT` not equal to `META` (`GRAY` or
     `RGB`), then calls `create_thumbnail`, which verifies that `DATA` has at
     least `bytes_needed` bytes (`payload.len >= bytes_needed`), allocates a
     buffer, copies `bytes_needed` bytes from `DATA`, touches the first and
     last bytes via `observation_sink`, frees the buffer, and returns 1.


2. Harness

Explain what your harness passes to the parser and why the harness is suitable
for repeated in-process execution.

In `fuzz_target.c`, `LLVMFuzzerTestOneInput` passes the fuzzer-supplied buffer
`data` and byte length `size` directly to `parse_image_message(data, size)`
once per iteration and returns 0. It is suitable for repeated in-process
execution because it performs no file or console I/O, does not call `exit()` or
`abort()`, frees any dynamically allocated heap memory inside `create_thumbnail`
before returning, and relies on no persistent per-input state that alters
control flow across invocations (`observation_sink` is only written to prevent
dead-code elimination).

7. Crash minimization

Original crash size: 358 bytes
Minimized crash size: 351 bytes
Explain which parts of the minimized input are required to reach the bug.

To reach the failing `memcpy` in `create_thumbnail`, the minimized input must
contain:
1. The `IMG2;` header at the start of the message.
2. A non-`META` format (`FMT=RGB;`, 3 channels).
3. `OP=THUMB;` and `AUTH=YES;` to pass the operation and authorization checks.
4. Valid dimensions `W=6;` and `H=17;` (between 1 and 64) whose product with
   `channels` yields `bytes_needed = 6 * 17 * 3 = 306 >= 256`, causing
   `(uint8_t)bytes_needed` to truncate to a 50-byte allocation (`306 % 256 = 50`).
5. A `DATA=` field containing at least 306 bytes prior to `;` so the
   `payload.len < bytes_needed` check passes and `memcpy` writes 306 bytes into
   the 50-byte heap buffer (306 payload bytes + 45 header/field bytes = 351 bytes
   minimum).


8. Corpus minimization

Corpus size before minimization: 61 files
Corpus size after minimization: 48 files (6125 bytes)
Explain what the minimized corpus preserves.
Corpus minimization (`-merge=1`) preserves the union of all coverage edges and
coverage features (`cov: 89` and `ft: 220`) discovered across the original
61-file corpus while selecting a smaller subset of 48 files that achieve that
exact same coverage. Unlike crash minimization, which shrinks a single failing
input while preserving a specific sanitizer error, corpus minimization reduces
a collection of non-crashing inputs while preserving overall code coverage
across the parser.


9. Program fix

Describe the code change and explain why it prevents the memory error while
preserving the intended operation. Summarize your regression-test and final
sanitizer results.

- Code change: In `create_thumbnail` (`image.c`), removed the narrowing cast
  `uint8_t allocation_size = (uint8_t)bytes_needed;` and passed `bytes_needed`
  (type `size_t`) directly to `malloc(bytes_needed)`.
- Why it prevents the error: `width` and `height` can each be up to 64 and
  `channels` can be up to 3, so `bytes_needed` can reach 12,288 bytes. Casting
  `bytes_needed` to `uint8_t` truncated any value >= 256 modulo 256, causing
  `malloc` to allocate a buffer smaller than `bytes_needed` before `memcpy`
  copied `bytes_needed` bytes into it. Allocating `malloc(bytes_needed)`
  directly ensures the heap buffer always matches the exact number of bytes
  copied by `memcpy`.
- Validation and regression results: Rebuilt `image`, `image-asan`, and
  `fuzz_target` cleanly. `make test` passed all normal-input tests (`accepted`
  for `info.img`, `gray-check.img`, `meta-check.img`, and `rejected` for
  `invalid.img`). Replaying both the original 358-byte crash artifact and the
  351-byte `minimized-crash.img` through `./image-asan` and `./fuzz_target`
  completed with zero sanitizer errors (`accepted`). A final 30-second
  sanitizer-enabled fuzzing campaign against the repaired binary completed
  without triggering any crashes.
